> История Go-издания: упоминания Go-команд, путей и цифр ниже относятся к Go-реализации (ai386).

## Context

На текущий момент (`machine-core` + `config-cli`, см. proposal.md — Why) машина имеет только байтовую шину: `Bus.ReadMem/WriteMem` (byte), `Bus.In/Out` (byte), приоритет диапазонов устройств над RAM, жизненный цикл Start/Stop без исполнителя кода. `go.mod`: Go 1.26, testify, toml. Исполнителя нет — это и есть предмет change.

## Goals / Non-Goals

**Goals:**
- Интерпретатор полного набора i386/i486 в пакете `internal/cpu`, исполняющий одну инструкцию за шаг и пригодный к интеграции с будущими устройствами.
- Расширение шины широкими доступами без изменения байтовой маршрутизации устройств.
- Табличная тестовая база: внешний набор SingleStepTests/80386 (real mode) + собственные таблицы для защищённого режима, paging, v86 и 486-дополнений.

**Non-Goals:**
- Точность по циклам и микроархитектуре (prefetch, pipeline) — только семантическая.
- Полноценный цикл исполнения машины с прерываниями по времени и внешними устройствами (задача этапа 4/BIOS).
- Реализация x87 (отдельный change); на текущем этапе опкоды D8–DF → #UD.

## Decisions

### D1: Пакет `internal/cpu`, плоская раскладка файлов
Без вложенных подпакетов; файлы по темам:
- `cpu.go` — структуры состояния, конструктор, сброс, `Step()`/`Run()` цикл;
- `decode.go` — таблицы декодера, обработка префиксов, ModRM/SIB, выбор обработчика;
- `alu.go` — арифметика/логика/флаги; `move.go` — пересылки; `control.go` — переходы; `string.go` — строковые с REP; `system.go` — системные и привилегированные; `protmode.go` — сегментация/дескрипторы/привилегии/TSS; `paging.go` — страничная трансляция; `exception.go` — генерация и доставка исключений.
Почему: Bochs-стиль, проверенный практикой для интерпретаторов; максимум читаемости и изоляции тестов. Альтернатива (вложенные подпакеты) ведёт к избыточности общих типов.

### D2: Табличный декодер
Главная таблица из 256 записей + вторая для префикса `0F`. Запись несёт обработчик, допустимость префиксов (REP/LOCK/сегмент), признак строковой/привилегированной инструкции. Префиксы 0x66/0x67 меняют размер операндов/адреса, накапливаются в контексте шага; неопределённые комбинации дают #UD.
Почему: полный набор кодируется декларативно, а не сотнями веток в одном switch; новые инструкции добавляются одной строкой таблицы. Альтернатива (монолитный switch) непомерно разрастается на полном наборе.

### D3: Состояние процессора и кэш сегментных дескрипторов
`CPU` хранит регистры (GPR, EIP, EFLAGS, сегментные CS/SS/DS/ES/FS/GS, CR0/CR2/CR3, DR0–DR7). У каждого сегмента — кэш {base, limit, ar, valid}, обновляемый при загрузке сегмента; в реальном режиме base = сегмент<<4, limit = 0xFFFF.
Почему: без кэша каждая выборка/обращение к памяти требует пересчёта и делает защищённый режим неоправданно медленным. Альтернатива (вычисление на лету) — проще, но сводит производительность интерпретатора к неприемлемо низкой.

### D4: CPU обращается к шине через локальный интерфейс
`internal/cpu` определяет узкий интерфейс `MemoryBus { Read8/16/32, Write8/16/32, In/Out8/16/32 }`, реализованный `*machine.Bus`. Пакет `cpu` не импортирует `machine`, тесты подставляют фейковую шину.
Почему: развязка пакетов (нет циклических импортов), юнит-тесты легко изолируют память. Альтернатива (прямой импорт `machine`) связывает CPU с машиной и мешает тестированию.

### D5: Расширение шины широкими доступами
`Bus` получает `Read16/Read32/Write16/Write32` и `In16/In32/Out16/Out32`. Реализация — маршрутизация по байтам через существующие `ReadMem/WriteMem/In/Out`, сохраняя действующий приоритет `memoryRanges` над RAM и байтовую обработку устройств.
Почему: минимальное изменение ядра, широкий доступ гарантированно согласован с байтовым поведением устройств. Альтернатива (wide-интерфейс у каждого устройства) меняет все устройства разом и опережает их появление.

### D6: Исполнение по шагам
CPU предоставляет `Step()` (одна инструкция) и `Run(n)` (n шагов с проверкой прерываний между инструкциями). `Machine.Start` производит reset CPU (CS=0xF000, EIP=0x0000FFF0) и связывает шину; активный цикл с устройствами/таймерами включается на этапе BIOS.
Почему: `Step()` идеален для табличных тестов; `Run(n)` закрывает будущую интеграцию. Альтернатива (бесконечный цикл внутри Start) несовместима с тестами и требованиями этапа.

### D7: Трансляция адресов
Каждый доступ к памяти проходит цепочку: эффективный адрес (ModRM/SIB + смещение, с учётом 0x67) → линейный (сегмент base + offset, проверка лимита по кэш-дескриптору) → физический (paging при CR0.PG: директории/таблицы по CR3, страницы 4K/4M; нарушение → #PF, адрес в CR2). Нарушения сегментных прав → #GP/#SS.
Почему: единая точка трансляции; режимы real/protected/v86 отличаются только правилами формирования линейного адреса и проверок.

### D8: Прерывания и исключения — только сторона CPU
Исключения генерируются внутри (`#UD`, `#DE`, `#GP`, `#PF`, `#SS` и др.), аппаратные запросы приходят через `CPU.RequestInterrupt(n)`. Доставка: в реальном режиме — IVT (4 байта на вектор), в защищённом — IDT через `lidt`; фрейм (флаги, CS, IP/EIP, код ошибки) кладётся на стек с учётом типа и размера операнда. Между инструкциями проверяется взвешенный pending-запрос.
Почему: этап ограничен CPU-стороной (решение пользователя); PIC/8259 — позже, интерфейс `RequestInterrupt` уже совместим.

### D9: Тесты — гибрид
- **Внешний набор**: конвертация `SingleStepTests/80386` (`moo2json.py`, ветка `v1_ex_real_mode`) в `internal/cpu/testdata/80386/` + файл лицензии MIT. Загрузчик парсит JSON, применяет `initial`, делает `Step`, сверяет `final`-регистры, память и `exception`. Маски неопределённых флагов — из `80386.csv` (`f_umask`). Циклы набора игнорируются (386EX, 16-бит шина).
- **Собственные таблицы**: слайсы структур `{imem, iregs, iflags, mem...}` → ожидаемые `{regs, flags, exception}` для защищённого режима, paging, v86, инструкций 486-класса, недоступного внешнему набору.
Почему: замкнутый цикл с самостоятельной верификацией; набор 386 уже отлажен и проверен на реальном железе, что повышает точность real-mode части. Альтернатива (только свои таблицы) выше риск расхождения с реальным CPU.

### D10: FPU-опкоды → #UD
Диапазоны D8–DF декодируются как инструкции x87 и на текущем этапе всегда генерируют #UD (вектор 6). Это документировано в спеке; change FPU заменит обработчик.
Почему: честное поведение до реализации x87 вместо молчаливого пропуска; isolate scope.

## Risks / Trade-offs

- [Объём полного набора инструкций большой, растягивается на много задач] → декомпозиция задач по семьям инструкций с табличными тестами для каждой; набор 386 даёт немедленную обратную связь.
- [Внешний набор привязан к реальному 386 (не i486): часть семантики флагов/исключений и 486-дополнений не покрыта] → собственные таблицы закрывают разрыв; базовые кейсы сверяются с 386-набором.
- [Размер набора 80386 (диапазон «100–2500 на опкод») может раздуть репозиторий] → оценить объём на импорте, при необходимости — vendor подмножеством (по опкодам) либо обобщение загрузчика `testdata` по требованию.
- [Производительность интерпретатора] → замер на этапе интеграции (этап 4); оптимизация — отдельные пакеты без изменения интерфейсов (оговаривает design.md roadmap).
- [Неопределённые флаги (например, OF для сдвигов, AF для логических) могут «провалить» сверку] → маски `f_umask` из 80386.csv; собственные таблицы не проверяют неопределённое.

## Open Questions

- Тот ли подмножество 80386 vendor'ится (весь real mode vs выборочные опкоды) — определится по факту объёма на этапе реализации, не влияет на спеки.
- Нужен ли отдельный публичный `Run()` метод уже на этапе 2 или только `Step()` — решается при интеграции машины, не меняет поведенческие требования.

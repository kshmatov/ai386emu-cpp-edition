## Контекст

При `clock_hz=100 МГц` эмулятор выполняет ~8.5×10⁶ cycles/s wall
(≈ 0.085× realtime). Нажатие клавиши хостом 100–200 мс wall соответствует
8–16 мс **виртуального** времени. Doom опрашивает ввод на тиках 35 Гц
(≈ 28 мс виртуальных). Make+break успевают «проскочить» между опросами
или уходят в одном tic — меню не доходит до Quit, I_ShutdownGraphics не
вызывается, BDA449 остаётся 13h, пользователь видит чёрный graphics-кадр.

При `clock_hz=1 МГц` virtual/real ≈ 8× — те же нажатия живут сотни мс
виртуального времени, quit проходит.

## D1. Норма — виртуальное время, не wall-clock

Длительность видимости make-скан-кода гостю задаётся в виртуальном
времени (мс или PIT-тиках), аналогично `sb16.Advance` / `pit.Advance`.
Например: не снимать make, пока не прошло ≥ 50 мс виртуального времени
**и** гость не считал байт; break — после минимума либо немедленно, если
make уже прочитан и минимум истёк.

Конкретный минимум — параметр/константа в одном месте (не CLI), с
регрессией на границе. Значение подобрать так, чтобы пережить тик Doom
35 Гц с запасом (≥ 1–2 тиков, т.е. ~30–60 мс виртуальных).

## D2. Кто удерживает

Предпочтительно `internal/ps2.Controller`: очередь уже хранит байты;
нужно не отдавать break раньше срока и/или держать last make до
минимальной виртуальной длительности. Хост/frontend продолжает слать
make/break как сейчас; **семантика длительности** — в устройстве.

Альтернатива (отклонена как основная): frontend растягивает wall-удержание
— зависит от FPS/UI и не лечит headless/API `Machine.KeyEvent`.

## D3. Регрессия Doom quit

Сценарий на копии `freedos-ready.img`:

1. Boot → DOS → `DOOM -NOSOUND -WARP 1 1` → 320×200, непустой кадр.
2. Esc (menuActive=1), 5×Down (Quit), Enter, Y.
3. Критерий: BDA449=03, TextGeometry≠0, на экране `C:\` (или ENDOOM +
   prompt), CPU не в игровом цикле mode 13h.
4. Прогнать при `clock_hz=1_000_000` **и** `100_000_000`.
5. Негатив: без hold-фикса сценарий на 100 МГц red (как воспроизведено).

Длительность нажатий в тесте — в шагах/виртуальных мс, а не wall.

## D4. Производительность (смежный замер, не blocker hold-фикса)

Замер 2026-10-15:

- ~4–5.6 млн `Machine.Step`/s;
- ~8.5 млн cycles/s на memory-loop;
- INT 1A hook почти не добавляет bus cycles → `ClockCycles` ≈ 0, но
  `Step` учитывает `max(delta, 1)` — тики всё же идут, медленно.

README: для интерактивной игры при ожидаемой отзывчивости указать
`clock_hz` ≈ 1–10 МГц либо терпение при 100 МГц. Default 100 МГц
отдельно не менять в этом change.

## Альтернативы (отклонены)

- **Ускорить интерпретатор до 100 MIPS** — вне объёма; без этого
  виртуальное время всё равно отстаёт.
- **Понизить default clock_hz** — меняет таймеры всех ОС; после hold-фикса
  и замеров.
- **Игнорировать break совсем** — ломает залипание клавиш.

## Context

Этап 2 завершил реализацию CPU i486 и базовой шины. Текущее состояние:
- `Machine` создаёт RAM, Bus и CPU
- `Bus` поддерживает регистрацию портов и диапазонов памяти через интерфейсы `PortDevice` и `MemoryDevice`
- CPU обращается к памяти/портам через `MemoryBus` interface
- HD создаётся как пустой плейсхолдер, не используется

Этап 3 должен реализовать полную подсистему хранения: block devices, IDE PIO контроллер, floppy controller и представление каталога хоста как CD (shared CD).

## Goals / Non-Goals

**Goals:**
- Реализовать block device абстракцию для HD, CD и floppy
- Реализовать IDE PIO контроллер с двумя каналами (primary/secondary)
- Реализовать floppy controller (1.44M, PIO)
- Поддержать ISO9660 image файлы для CD
- Поддержать представление каталога хоста как read-only CD (shared CD) без материализации ISO-файла на диске
- Интегрировать устройства с Bus и Machine

**Non-Goals:**
- DMA не реализуется (PIO only)
- ATAPI protocol не реализуется (только basic IDE commands)
- Динамическое изменение размера HD
- Запись на CD/ shared CD
- Поддержка не-ISO9660 форматов CD (UDF и т.д.)
- Отражение изменений каталога хоста после старта VM (снимок фиксируется при старте)

## Decisions

### D1: Архитектура block device

```
┌─────────────────────────────────────────────────────────────┐
│                    ARCHITECTURE                              │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  storage/block.go — BlockDevice interface                    │
│    ReadSector(n) → []byte                                   │
│    WriteSector(n, data)                                     │
│    SectorSize() → int                                       │
│    NumSectors() → int                                       │
│    ReadOnly() → bool                                        │
│                                                              │
│  storage/raw.go — rawDataStore implements BlockDevice        │
│    Файловый backed, фиксированный размер сектора (512 байт) │
│    Для HD и floppy                                          │
│                                                              │
│  storage/iso.go — isoDataStore implements BlockDevice        │
│    ISO9660 backed, 2048 байт/сектор                         │
│    Для CD-ROM из ISO-файла                                  │
│                                                              │
│  storage/iso_virtual.go — virtualIsoStore implements BlockDevice │
│    Метаданные ISO9660 (PVD + directory records) строятся     │
│    в памяти при старте из каталога хоста; данные секторов    │
│    читаются напрямую из host-файлов по LBA-диапазону          │
│    Для shared CD (без записи .iso на диск)                   │
│                                                              │
│  storage/ide.go — IDEController implements PortDevice        │
│    PIO mode, 2 channels, READ/WRITE/IDENTIFY                 │
│                                                              │
│  storage/fdc.go — FloppyController implements PortDevice     │
│    1.44M, READ/WRITE/RECALIBRATE/SENSE                      │
│                                                              │
│  Machine интеграция:                                         │
│    Machine.New() → создаёт HD/FD/CD devices                  │
│    Bus.RegisterPorts() для каждого контроллера               │
│    Bus.RegisterMemory() не нужен (только порты)              │
└─────────────────────────────────────────────────────────────┘
```

**Альтернативы:**
- Монолитный контроллер (один класс для всех устройств) — отвергнут: нарушает разделение ответственности
- Отдельный интерфейс для каждого типа — отвергнут: избыточно, все устройства — block devices

### D2: Формат HD-образа

Raw image, фиксированный размер. Один сектор = 512 байт. Файл создаётся `os.Create` + `Truncate` до нужного размера при первом запуске.

**Альтернативы:**
- qcow2/dynamic — отвергнут: сложность без выигрыша на текущем этапе
- Sparse file — отвергнут: не переносимо между ФС

### D3: ISO9660 парсинг (файл) и виртуальное ISO9660 (shared CD)

Для чтения ISO-файла: парсинг Primary Volume Descriptor (sector 16), directory records, файловый доступ по логическому блоку (2048 байт).

Для shared CD (каталог хоста) — виртуальное, ленивое ISO9660-представление без материализации файла:
- при старте VM каталог хоста обходится один раз; в памяти строится только метаданные: один Volume Descriptor, дерево directory records и таблица отображения "LBA-диапазон → (host-путь, смещение)"; сами данные файлов не копируются и не буферизуются
- при чтении сектора `virtualIsoStore` определяет по LBA, попадает ли запрос в область метаданных (отдаётся из памяти) или в область данных файла (читается напрямую из host-файла через `os.File.ReadAt` на нужном смещении)
- итоговый .iso-файл на диске не создаётся; для гостевой ОС устройство неотличимо от обычного ISO9660 CD-ROM
- без Joliet/Rock Ridge (стандартного ISO9660 достаточно для базового доступа к файлам)
- почему не паравиртуальный доступ (9p/virtio-fs): целевые гостевые ОС (Linux/FreeBSD эпохи i486) не имеют драйверов virtio/9p — эти механизмы появились на 15+ лет позже; сетевой доступ (NFS/SMB) требует настроенного сетевого стека в госте и зависит от ещё не реализованного этапа `network` — не подходит для простого "подключил CD и увидел файлы"

**Альтернативы:**
- Использовать готовую библиотеку (e.g. go-iso9660) — отвергнут: минимизация зависимостей
- Генерировать полноценный .iso-файл на диске перед стартом — отвергнут: лишнее использование диска и времени старта, требует пересборки при каждом изменении каталога
- Монтировать как 9p/virtio — отвергнут: гостевые ОС этой эпохи не поддерживают такие драйверы

### D4: IDE PIO команды

Реализуются только базовые команды:
- `0xEC` — IDENTIFY DEVICE
- `0x20` — READ SECTORS (with retries)
- `0x30` — WRITE SECTORS (with retries)
- `0x00` — NOP (для сброса)
- Остальные команды возвращают ошибку (ABRT в статусе)

### D5: Интеграция с конфигурацией

Новые флаги CLI:
- `--hd-size <size>` — размер HD при создании (по умолчанию 1G)
- `--shared <path>` — каталог для shared CD
- `--floppy <path>` — путь к floppy-образу

Новые параметры TOML:
- `HDSize = "1G"`
- `Shared = "/path/to/dir"`
- `Floppy = "/path/to/floppy.img"`

## Risks / Trade-offs

- [ISO9660 парсинг может быть неполным] → Используется minimal subset (PVDescriptor + directory traversal); тесты на реальных ISO
- [Нет ATAPI — CD не будет работать с некоторыми ОС] → Базовые CD-операции через IDE; ATAPI отложен
- [Виртуальное ISO9660-представление каталога может не покрывать все edge cases (вложенность, длинные имена)] → Тесты на простых каталогах; расширяемость заложена в структуру directory records
- [PIO медленнее DMA] → Достаточно для установки и работы ОС; оптимизация отложена
- [Нет поддержки multi-sector transfer в PIO] → Реализуется basic multi-sector; производительность приемлема

## Resolved during implementation

- **Границы «статичности снимка» (D3) для virtualIsoStore**: снимок фиксирует ДЕРЕВО каталога (имена, размеры, LBA-раскладку directory records) один раз при старте — файлы/каталоги, добавленные или удалённые в host-каталоге после построения, не появляются и не исчезают со структуры устройства. Данные уже проиндексированных файлов читаются лениво через `os.File.ReadAt` без буферизации (прямое следствие явного требования D1/D3 не копировать данные при старте) — если host-файл, уже присутствующий в дереве, был изменён после старта VM, гостевая ОС при чтении увидит актуальные байты хоста. Это осознанный компромисс между «полный снимок» и «не буферизовать данные»: копирование всех данных при старте противоречило бы D3, поэтому зафиксирована только структура.
- **PIO data-регистр IDE — только байтовый доступ**: `Bus.In16/Out16` в этом проекте компонует широкий доступ из двух соседних 8-битных портов (port, port+1), что не соответствует семантике реального IDE data-регистра (16-битное слово по ОДНОМУ порту 0x1F0). Чтобы не переделывать общую семантику шины (стабильна с этапа 2), IDE data-регистр реализован для байтового PIO-режима (ATA поддерживает byte I/O как штатный режим). Контроллеры/тесты обращаются к `IDEChannel.In/Out` напрямую по одному байту за раз.
- **Формат identify-блока и байтовый порядок ASCII-полей**: реализовано без стандартного ATA word-swap строк (модель/серийный номер хранятся в естественном порядке байт) — упрощение, так как строгое соответствие реальному ATA не требуется для собственного минимального BIOS следующего этапа; сам эмулятор внутренне согласован.
- **Геометрия CHS**: 16 головок × 63 сектора/дорожку (общепринятая LBA-совместимая трансляция) для IDE HD/CD; для floppy — стандартная геометрия 1.44M (80/2/18).
- **Слоты IDE для нескольких `--cd`/`--shared`**: физически доступно 4 позиции IDE (Primary/Secondary × Master/Slave), из них Primary Master зарезервирован под HD. Реализовано: первый `--cd` → Primary Slave; первый `--shared` → Secondary Master; второй `--shared` → Secondary Slave. Дополнительные пути `--cd` (второй и далее) и `--shared` (третий и далее) не подключаются — свободных слотов не остаётся на одном двухканальном IDE-контроллере. Это соответствует зафиксированным в D5 позициям (Primary Slave для `--cd`, Secondary Master для `--shared`) и реалистичным аппаратным ограничениям PIO IDE этой эпохи; расширение (третий канал/несколько контроллеров) не является целью этапа.
- **Path Table в виртуальном ISO9660**: не генерируется (Location/Size = 0). Гостевые ОС этой эпохи (Linux isofs, FreeBSD cd9660) монтируют ISO9660, рекурсивно обходя directory records от корня, а не через path table — она была оптимизацией для MS-DOS. Отсутствие Path Table не мешает чтению файлов.

## Open Questions

- Поддержка multi-word DMA для floppy — решаем: нет, PIO only
- Нужна ли поддержка CHS addressing или достаточно LBA — решаем: оба варианта (BIOS может использовать CHS)
- Формат загрузочного сектора HD — решается на этапе 4 (BIOS)

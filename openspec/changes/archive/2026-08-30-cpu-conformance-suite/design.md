> История Go-издания: упоминания Go-команд, путей и цифр ниже относятся к Go-реализации (ai386).

## Context

Этап 2 импортировал вендоренный набор SingleStepTests/80386 (`internal/cpu/testdata/80386`, 941 файлов, 37 640 тестов) специально для отлова расхождений с эталонным поведением 80386, но он так и не был подключён как реальный conformance-раннер — только структурная проверка JSON (`testdata_load_test.go`). При отладке этапа 4 (BIOS) был найден баг CPU (`0x83`, см. ), который такой раннер отловил бы немедленно.

При подготовке раннера обнаружилось, что сам корпус повреждён на уровне конвертера:

**Диагностика (воспроизведена и подтверждена в этой сессии):**
- `tools/moo2json/main.go` определяет 32-битный формат регистров MOO-файла условием `"386" == shorten(cpuName)` (точное совпадение строки).
- Скачан оригинал `v1_ex_real_mode/04.MOO.gz` из `github.com/SingleStepTests/80386`. Заголовок файла: `Cpu type: 386E`.
- `shorten("386E") == "386"` → `false` → конвертер ошибочно берёт 16-битную раскладку регистров (`ax,bx,cx,dx,cs,ss,ds,es,sp,bp,si,di,ip,flags`, маска 16 бит) вместо корректной 32-битной (`cr0,cr3,eax,ebx,ecx,edx,esi,edi,ebp,esp,cs,ds,es,fs,gs,ss,eip,eflags,dr6,dr7`, маска 32 бита).
- Референсная реализация (`python/moo2json.py` проекта dbalsom/moo, на формат которого ориентируется наш порт) использует `'386' in cpu_name` — подстроку, а не точное совпадение — и корректно распознаёт `"386E"`.
- Пересборка `04.MOO.gz` референсным скриптом даёт согласованные результаты: например, тест `add al,18h` с `initial.eax=2113472081` (0x7DEC0F51) даёт `final.eax=2113472105` (0x7DEC0F69) — разница ровно 0x18, арифметика верна. Вендоренный `04.json` для того же файла показывает **одинаковый** `final={"regs":{"cx":3}}` для всех проверенных тестов независимо от разных операндов — бессмысленный результат.
- Вывод: все 941 файла текущего вендоренного корпуса декодированы неверно и непригодны как эталон.

## Goals / Non-Goals

**Goals:**
- Исправить определение 32-битного формата в `tools/moo2json` (подстрока вместо точного совпадения).
- Перекачать исходные `*.MOO.gz` и перегенerировать `internal/cpu/testdata/80386/*.json` исправленным конвертером, с тем же сэмплированием (40 тестов/файл, `-per-file 40`), сохранив текущий объём репозитория (~48 МБ).
- Реализовать conformance-раннер: для каждого теста — установка полного состояния CPU из `initial` (регистры/сегменты/CR0/CR3/DR6/DR7, память), один `Step()`, сравнение итогового состояния с `final` (регистры — diff поверх `initial`, память — байты из `final.ram`, EFLAGS — с маской неопределённых битов из `80386.csv`).
- По результатам первого прогона на исправленных данных — найти и исправить реальные баги CPU (аналогично найденному и исправленному багу `0x83`).

**Non-Goals:**
- Расширение сэмпла сверх 40 тестов/опкод (полный набор — до 2500/опкод, ~1.5 ГБ несжатых данных — неприемлем для репозитория, см. существующий README).
- 100%-е прохождение абсолютно всех тестов любой ценой: если после разумных усилий остаются единичные необъяснённые расхождения по редким/периферийным кодировкам — они документируются как известное ограничение (с указанием опкода и характера расхождения), а не блокируют приёмку этапа бесконечным дебагом.
- Точное побайтовое соответствие `CR0`/`CR3`/`DR6`/`DR7` для инструкций, которые их не читают/не пишут: сравнение этих полей имеет смысл только когда исполняемая инструкция теста фактически их затрагивает (`MOV CR0/DR*`); для остальных тестов они переносятся через `initial` без изменений и совпадают тривиально.
- Эмуляция таймингов/шинных циклов (`cycles` в JSON) — раннер сравнивает только архитектурное состояние (регистры, память, флаги), не цикл-точную модель.

## Decisions

### D1: Фикс `tools/moo2json` — определение CPU по подстроке

`is386 := strings.Contains(strings.ToLower(cpuName), "386")` вместо точного сравнения. Строка встречается в двух местах (`decodeRegState`/вызов из `parseMOOBytes`, и аналогичная проверка в `decodeCycles` для интерпретации `bus_i`/`t_i` — свериться и поправить обе, если затронуты обе).

### D2: Перекачка и перегенерация корпуса

Источник: `https://github.com/SingleStepTests/80386/tree/main/v1_ex_real_mode` — 941 файлов `*.MOO.gz`, публичный домен (данные) / MIT (код), уже задокументировано в `internal/cpu/testdata/80386/README.md`. Скачать во временный каталог (не в репозиторий), прогнать `go run ./tools/moo2json -per-file 40 <tmp-dir> internal/cpu/testdata/80386`, удалить временные `*.MOO.gz`/`*.MOO` после конвертации (не коммитить сырые файлы — они большие и лицензионно уже покрыты ссылкой на источник в README, как и раньше). Обновить `README.md` датасета: дата перегенерации, факт исправления бага конвертера.

Сетевые запросы — обычные HTTPS GET к `raw.githubusercontent.com`/`api.github.com`, без аутентификации (публичный репозиторий).

### D3: Установка состояния CPU из `initial`

Раннер живёт в пакете `cpu` (не `cpu_test`) — как и существующий загрузчик `testdata_load.go` — чтобы иметь прямой доступ к внутренним полям CPU (`c.regs`, `c.eflags`, `c.seg`/`c.cache` через `SetSeg`, `c.cr0`/`c.cr3`/`c.dr6`/`c.dr7` или их текущие аналоги) без необходимости заводить экспортированный API ради теста.

Для каждого теста:
1. Создать CPU с тестовой шиной (аналог `testBus` из `decode_test.go`, расширенным для побайтовой инициализации памяти по `initial.ram`).
2. Установить регистры/сегменты/CR0/CR3/DR6/DR7 из `initial.regs` (ключи теперь `cr0,cr3,eax,ebx,ecx,edx,esi,edi,ebp,esp,cs,ds,es,fs,gs,ss,eip,eflags,dr6,dr7` — 32-битная раскладка после фикса D1/D2).
3. Записать байты `initial.ram` в память шины.
4. Выполнить один `c.Step()`.

### D4: Сравнение с `final`

- **Регистры**: `final.regs` — это только ИЗМЕНИВШИЕСЯ относительно `initial.regs` поля (подтверждено наблюдением: тесты без модификации памяти и без затронутых регистров дают `final.regs` с одним-двумя ключами, а не полным набором). Ожидаемое состояние = `initial.regs`, с применёнными поверх ключами `final.regs`. Сравнивается **каждое** поле ожидаемого состояния с фактическим состоянием CPU после `Step()`.
- **EFLAGS**: применяется маска `f_umask` из `80386.csv` для опкода теста (парсинг CSV через `encoding/csv`, с учётом кавычек в некоторых полях — не наивный `strings.Split` по запятой). Сопоставление опкода теста (имя JSON-файла, напр. `08.json`, `0FA4.json`, `FF.0.json`) со строкой `80386.csv` — по колонке `op` (регистронезависимо, с обрезкой суффикса подгруппы после точки для строк вида `FF.0`). Если для опкода нет строки в CSV или `f_umask` пуст — сравнивать все биты EFLAGS без маски.
- **Память**: для каждого `[addr, value]` в `final.ram` — байт по `addr` на тестовой шине должен равняться `value`.
- **Исключения**: если тест содержит `exception`, ожидается, что `Step()` привёл к доставке исключения с этим номером вектора (а не к обычному завершению инструкции с переходом в `final`) — раннер проверяет факт доставки (например, IP/CS указывают на обработчик из IVT для этого вектора), не полное совпадение `final`, так как `final` для тестов с исключением может отражать состояние на момент прерывания, а не после «обычного» выполнения.

### D5: Обработка находок

Каждая найденная и исправленная в ходе этой задачи ошибка CPU документируется по аналогии с фиксом `0x83`: причина, конкретная строка/файл, тест-регрессия. Если после разумных усилий остаются единичные необъяснённые расхождения на редких/периферийных кодировках — они фиксируются как известное ограничение (список опкодов + короткое описание расхождения) в README датасета или в самом раннере (например, `skipKnownIssues` с комментарием и ссылкой), не блокируя приёмку. Массовые (не единичные) расхождения по целому классу инструкций рассматриваются как настоящий баг CPU и исправляются, а не документируются как ограничение.

## Risks / Trade-offs

- [Перекачка ~600 МБ исходных `*.MOO.gz` требует сетевого доступа при регенерации] → одноразовая операция при выполнении этой задачи; в репозиторий, как и раньше, попадает только сжатый сэмплированный JSON.
- [Раннер может найти неожиданно много расхождений] → см. D5: разбираемся итеративно, при обнаружении систематической проблемы — чиним корень (как с `0x83`), единичные редкие случаи — документируем, не блокируем этап бесконечно.
- [CSV-парсинг `80386.csv` с кавычками в полях (`op1`/`op2` вида `"r16/32 m16"`)] → использовать `encoding/csv`, не самодельный сплит по запятой.
- [Сопоставление многобайтных/групповых опкодов (`0F`-префикс, `FF.0` подгруппы) со строками CSV] → сверяться по колонке `op` с учётом регистра и суффикса подгруппы; при отсутствии точного совпадения — не применять маску (полное сравнение EFLAGS), не падать с ошибкой.

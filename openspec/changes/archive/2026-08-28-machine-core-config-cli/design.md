> История Go-издания: упоминания Go-команд, путей и цифр ниже относятся к Go-реализации (ai386).

## Context

Проект в нулевой стадии — кода нет (см. proposal.md — Why). Маршрут проекта (change `project-roadmap`) фиксирует архитектурные решения на уровне всего проекта: шина + интерфейсы устройств (D1) и пошаговая готовность системы (D3). Этап 1 — первый технический: создаёт каркас, конфигурацию и CLI без какой-либо функциональной подсистемы (CPU, дисков и т.д.). Дизайн опирается на решения D1 и D3 маршрута и детализирует их на уровне пакетов.

## Goals / Non-Goals

**Goals:**
- Определить структуру Go-модуля и границы пакетов каркаса, конфигурации и CLI.
- Зафиксировать интерфейсы шины и устройств так, чтобы последующие этапы добавляли устройства без переделки ядра.
- Определить модель памяти и пространство портов ввода-вывода с маршрутизацией.

**Non-Goals:**
- Не проектируются CPU, диски, VGA и прочие подсистемы — только точки подключения.
- Не определяется формат/размер образа HD — в этапе 1 создаётся только плейсхолдер (см. proposal.md — Non-goals).
- Не реализуется исполнение инструкций и BIOS.

## Decisions

### D1: Структура Go-модуля
Модуль `gitverse.ru/kshmatov/ai386`, Go 1.26, разбиение на внутренние пакеты:

- `cmd/ai386` — точка входа: оркестрация запуска (собрать конфигурацию → создать машину → запустить → дождаться/остановить).
- `internal/config` — структуры конфигурации, значения по умолчанию, загрузка из TOML, валидация, парсинг строки объёма памяти (`--ram`).
- `internal/cli` — парсинг GNU-флагов, слияние `CLI > config > defaults`.
- `internal/machine` — жизненный цикл виртуальной машины, шина устройств, модель памяти (RAM + карта диапазонов).

Каждый пакет занимается одной ответственностью; каркас не зависит от CLI и конфигурации напрямую (получает собранную конфигурацию).
Альтернатива (монолит в `internal/emulator`) отвергнута: конфликтует с правилом «этапы не смешивать», устройства добавляются по одному.

### D2: Интерфейсы устройств и шина
Шина (маршрут D1) предоставляет два пространства: память (32-битные адреса, до 4 ГБ) и порты ввода-вывода (16-битные адреса). Устройства регистрируют диапазоны и получают обращения:

- порты: устройство регистрирует диапазон `[base, base+len)` и реализует чтение/запись байта порта;
- память: устройство регистрирует диапазон памяти и реализует чтение/запись по адресу.

Обращение к незарегистрированному порту: чтение возвращает `0xFF`, запись игнорируется — эмулятор не падает (требование «Чтение порта без устройства»). Обращение к памяти вне RAM и устройств аналогично не роняет эмулятор (определяется шиной).

Альтернатива (устройства как интерфейс с одним методом `Handle(access)` и разбором внутри каждого) отвергнута: дублирование логики маршрутизации в каждом устройстве и менее читаемая шина.

### D3: Модель памяти
RAM выделяется `[]byte` фиксированного размера из конфигурации. Физическое адресное пространство — 4 ГБ; RAM размещается с адреса 0. Диапазоны устройств (будущие VGA-память, BIOS, видеопамять) регистрируются поверх RAM и имеют приоритет при маршрутизации. Разметка верхних диапазонов решается на этапах VGA/BIOS (см. Open Questions).

Чтение/запись в RAM — прямой доступ по индексу; границы проверяются до обращения, чтобы избежать паники при выходе за пределы (требование «Недоступный адрес»).

### D4: Формат конфигурации и загрузка
Файл конфигурации — TOML (решение пользователя), парсинг через `github.com/BurntSushi/toml`. Структура файла:

```toml
hd = "disk.img"
cd = ["./iso1", "./iso2"]
ram = "32M"
boot = ["hd", "cd"]
```

Значения по умолчанию (когда параметр нигде не задан): RAM `32M`, CD — пустой список, очередь загрузки — `["hd", "cd"]` (см. Open Questions — набор допустимых устройств). Объём памяти принимается и в числовом виде (байты), и со суффиксами `K/M/G` (и `KB/MB/GB`) — парсится `internal/config`.

Валидация (требование «Недопустимый файл конфигурации»):
- RAM: положительное и не больше 4 ГБ;
- пути CD: должны существовать и быть каталогами;
- очередь загрузки: только допустимые имена устройств (см. D5);
- недопустимый TOML/отсутствующий файл → понятная ошибка с источником.

### D5: CLI и приоритет значений
Парсинг флагов через стандартный пакет `flag` (GNU-стиль, решений пользователя): `--hd`, `--cd` (повторяемый), `--ram`, `--boot`, `--config`. Порядок слияния: значения командной строки > файл конфигурации > значения по умолчанию (требование «Приоритет командной строки»).

Очередь загрузки — список имён устройств из фиксированного набора (`hd`, `cd`). Если имя не из набора — ошибка конфигурации (требование «Недопустимое устройство в очереди»).

### D6: Создание HD-плейсхолдера
Создание машины (жизненный цикл, `machine-core`) — момент, когда при отсутствии файла образа создаётся пустой файл-плейсхолдер (требование «Создание нового образа»). Существующий файл не изменяется и не открывается на запись без необходимости (требование «Использование существующего файла»). Реальную работу с образом (размер, формат, сектора) реализует этап `storage` — в этапе 1 файл не интерпретируется.

## Risks / Trade-offs

- [При архивации этого change дельты могут пересечься с дельтами маршрута `project-roadmap` по тем же областям] → при архивации проверить синхронизацию `machine-core` и `config-cli` в базовые спеки на дублирование, при необходимости уточнить формулировки.
- [`[]byte`-RAM просто копируется/мутируется, что небезопасно при будущих конкурентных обращениях устройств] → пока обращение однопоточное из цикла CPU; при необходимости ввести синхронизацию на этапе интеграции.
- [Допустимый набор `boot`-устройств (`hd`/`cd`) может оказаться узким для BIOS-этапа] → расширение набора не меняет интерфейсы конфигурации (спискок строк); отмечено в Open Questions.
- [Карта диапазонов шины линейно сканируется] → при росте числа устройств (≤ десятков на i486) перебор приемлем; оптимизация при необходимости отдельным пакетом.

## Migration Plan

Этап 1 — первый; существующего кода и пользовательских данных нет. Развёртывание заменяется переходом на новую ветку (git-flow) и сборкой; откат — отмена merge. Файлы конфигурации пользователями ещё не создаются (формат утверждается этим этапом и публикуется в README на этапе приёмки).

## Open Questions

- Формат и размер образа HD — решается на этапе `storage` (см. proposal.md).
- Разметка верхних диапазонов памяти (BIOS ROM, VGA-память, ACPI и пр.) — решается на этапах VGA и BIOS; шина уже поддерживает приоритетные диапазоны.
- Точный набор допустимых значений очереди загрузки (индексы CD, сеть и пр.) — уточняется на этапе BIOS.
- CLI-флаги и структура TOML утверждаются в файлах документации при приёмке этапа.

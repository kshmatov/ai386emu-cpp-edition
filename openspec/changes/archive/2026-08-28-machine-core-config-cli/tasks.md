# Tasks: Каркас, конфигурация и CLI (machine-core + config-cli)

> История Go-издания: упоминания Go-команд, путей и цифр ниже относятся к Go-реализации (ai386).

Этап 1 проекта ai386. Каждая задача завершается записью в  (время выполнения и токены). Работа выполняется одним субагентом на ветке по git-flow; этапы не смешиваются. Все задачи сопровождаются юниттестами (testify).

## 1. Инициализация модуля и зависимостей

- [x] 1.1 Создать `go.mod` (модуль `gitverse.ru/kshmatov/ai386`, Go 1.26) и структуру пакетов: `cmd/ai386`, `internal/config`, `internal/cli`, `internal/machine`; подключить заввисимости (testify, BurntSushi/toml). Критерий приёмки: `go build ./...` и `go vet ./...` проходят. Шаг журналирования: время и токены.

## 2. Каркас виртуальной машины (machine-core)

- [x] 2.1 Реализовать шину и интерфейсы устройств: регистрация диапазонов портов ввода-вывода и памяти, маршрутизация обращений. Критерий приёмки: юниттесты покрывают сценарии «Подключение устройства с диапазоном портов» и «Чтение порта без устройства» (чтение незарегистрированного порта возвращает 0xFF, эмулятор не падает). Журнал.
- [x] 2.2 Реализовать модель памяти: RAM из заданного объёма, чтение/запись, приоритет диапазонов устройств над RAM, безопасное поведение для недоступных адресов. Критерий приёмки: юниттесты покрывают сценарии «Чтение и запись в RAM», «Обращение к памяти устройства», «Недоступный адрес». Журнал.
- [x] 2.3 Реализовать жизненный цикл машины: создание с RAM и устройствами из конфигурации, переход в состояние сброса при запуске, останов с освобождением ресурсов, повторный останов без ошибки. Критерий приёмки: юниттесты покрывают сценарии «Запуск машины», «Остановка машины», «Повторная остановка». Журнал.

## 3. Конфигурация (config-cli)

- [x] 3.1 Реализовать структуру конфигурации и значения по умолчанию (RAM `32M`, CD — пусто, очередь загрузки `["hd", "cd"]`); парсинг объёма памяти с суффиксами (`K/KB/M/MB/G/GB`) и в байтах. Критерий приёмки: юниттесты на парсинг значений и дефолты. Журнал.
- [x] 3.2 Реализовать загрузку конфигурации из TOML (пути HD и CD, объём RAM, очередь загрузки). Критерий приёмки: юниттесты на чтение корректного файла и понятные ошибки для отсутствующего файла и невалидного TOML (сценарий «Недопустимый файл конфигурации»). Журнал.
- [x] 3.3 Реализовать валидацию конфигурации: RAM в диапазоне (0 < RAM ≤ 4 ГБ), пути CD существуют и являются каталогами, очередь загрузки содержит только допустимые устройства (`hd`, `cd`). Критерий приёмки: юниттесты на каждое правило валидации (включая сценарии «CD-путь без каталога» и «Недопустимое устройство в очереди»). Журнал.

## 4. CLI и приоритет значений (config-cli)

- [x] 4.1 Реализовать парсинг GNU-флагов: `--hd`, `--cd` (повторяемый), `--ram`, `--boot`, `--config`. Критерий приёмки: юниттесты на парсинг каждого флага, включая повторяющийся `--cd`. Журнал.
- [x] 4.2 Реализовать слияние источников конфигурации с приоритетом `CLI > файл конфигурации > defaults`. Критерий приёмки: юниттесты покрывают сценарии «Приоритет командной строки» и «Запуск с файлом конфигурации» (сохранённые очередь загрузки и RAM применяются при создании машины). Журнал.

## 5. Интеграция точки входа (cmd/ai386)

- [x] 5.1 Реализовать `main`: сборка конфигурации из CLI и файла, создание машины, запуск и останов, вывод понятных ошибок. Критерий приёмки: e2e-проверка `go run ./cmd/ai386 --config <валидный.toml>` завершается успешно (код 0), при невалидной конфигурации — код ошибки и сообщение в stderr. Журнал.
- [x] 5.2 Реализовать создание HD-файла: при отсутствии файла образа создаётся пустой плейсхолдер при создании машины; существующий файл не изменяется. Критерий приёмки: юниттесты покрывают сценарии «Использование существующего файла» и «Создание нового образа» (после запуска файл создан; существующий файл не тронут). Журнал.

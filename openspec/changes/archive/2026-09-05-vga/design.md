## Context

Текущее состояние (этапы 1–4):
- `internal/machine/bus.go` — шина с регистрацией диапазонов памяти (`RegisterMemory`) и портов (`RegisterPorts`); устройство реализует `machine.MemoryDevice`/`machine.PortDevice` (побайтовые `Read/Write`/`In/Out`, широкие обращения собираются шиной автоматически). Диапазоны регистрируются один раз при создании `Machine` и не могут быть впоследствии сняты (`Bus` не имеет метода анрегистрации) — это ограничивает то, как VGA может реагировать на переключение memory map (см. D2).
- `internal/bios/int10.go` — `hookInt10` (design.md bios-boot, D4): CF=0, без побочных эффектов. По решению этого change — заменяется делегированием в `vga`.
- Обсуждены и приняты пользователем три решения, определяющие архитектуру этапа:
  1. Вывод — только framebuffer/API наружу; реального окна в этом этапе нет (см. proposal.md Non-Goals).
  2. Объём режимов — «полный VGA» (включая Mode X/unchained), а не только стандартные BIOS-режимы 00h–13h.
  3. Верификация — юнит-тесты на регистры/форматы адресации плюс ручная визуальная проверка (нужен вспомогательный дамп кадра, не автоматический пиксельный эталон).

## Goals / Non-Goals

См. proposal.md (What Changes / Non-Goals). Дополнительно к design:

**Goals:**
- Эмулировать VGA на уровне регистров и памяти достаточно точно, чтобы все текстовые и графические режимы, включая Mode X, работали как следствие корректной реализации регистров — без специального кода под конкретные «известные» режимы.
- Дать чистую границу между «аппаратно точным» API (порты/память — то, что видит гостевой код и BIOS) и «наблюдательным» API (кадр в RGB — то, что видит тестовая/будущая фронтенд-инфраструктура, гостевой код о нём не знает).

**Non-Goals:** см. proposal.md.

## Decisions

### D1: VGA — устройство на шине, единый диапазон видеопамяти

`internal/vga.VGA` реализует `machine.MemoryDevice` и `machine.PortDevice`, как устройства хранения этапа 3. `Machine.New()` создаёт `vga.New()` и регистрирует:
- Память: **один** диапазон `0xA0000`–`0xBFFFF` (128 KiB) через `bus.RegisterMemory` — целиком, независимо от текущего Memory Map Select (см. D2): `Bus` не поддерживает динамическую перерегистрацию диапазонов, а весь VGA-адресный диапазон и так принадлежит только видеокарте на реальном железе, поэтому регистрация «с запасом» не создаёт конфликтов с другими устройствами.
- Порты: `0x3B4`–`0x3B5`, `0x3BA`, `0x3C0`–`0x3CF`, `0x3D4`–`0x3D5`, `0x3DA` — все стандартные VGA-порты одним или несколькими смежными диапазонами.

**Альтернативы:**
- Регистрировать только активный под-диапазон памяти и перерегистрировать при смене Memory Map Select — отвергнуто: потребовало бы добавить в `Bus` метод анрегистрации ради VGA-специфичного случая, тогда как проверка диапазона внутри `vga.Read/Write` (D2) достигает того же результата без изменения `machine-core`.

### D2: Memory Map Select — трансляция адреса внутри устройства

Регистр 6 (Miscellaneous) графического контроллера, биты 3–2, определяют активное окно:
- `00` — `0xA0000`–`0xBFFFF` (128 KiB, используется графическими режimами, включая chained mode 13h и unchained Mode X)
- `01` — `0xA0000`–`0xAFFFF` (64 KiB, режимы EGA/VGA 0Dh–10h/12h)
- `10` — `0xB0000`–`0xB7FFF` (32 KiB, монохромный текст)
- `11` — `0xB8000`–`0xBFFFF` (32 KiB, цветной текст)

`vga.Read(addr)`/`vga.Write(addr, val)` получают полный физический адрес (в диапазоне D1) и **первым делом** проверяют, попадает ли он в активное окно текущего значения Memory Map Select; адреса вне активного окна не читаются/не пишутся (чтение — `0xFF`, запись — игнорируется) — так же ведёт себя настоящий VGA. Планарная адресация внутри окна (сдвиг на 4 битовые плоскости, латчи) — предмет D4.

### D3: Публичный Go API — граница «аппаратное» / «наблюдательное»

`internal/vga` экспортирует два независимых слоя API:

1. **Аппаратный** — то же самое, что видит гостевой код: `Read`/`Write` (память), `In`/`Out` (порты). Единственный канал, которым пользуется ОС/загрузчик после передачи ей управления.
2. **BIOS-удобства** — небольшой набор методов, которыми пользуется `internal/bios` (native Go BIOS, design.md bios-boot D1/D3 — тот же принцип: нативный Go-код вместо исполнения настоящего ROM):
   - `SetMode(mode uint8) error` — программирует полный набор регистров (CRTC/секвенсер/графический/атрибутный/DAC) и очищает видеопамять для одного из стандартных BIOS video mode number (00h–13h); аналогично тому, как настоящий BIOS ROM программирует те же регистры при `INT 10h AH=00h` — здесь это делает Go-код напрямую, не интерпретируя гостевые инструкции.
   - `WriteChar(row, col int, ch byte, attr uint8)` и `ScrollUp(attr uint8)` — запись символа/атрибута в текстовый буфер текущего режима и прокрутка на одну строку; нужны `hookInt10`, чтобы не дублировать в `internal/bios` знание о раскладке текстовой памяti (шаг между символами зависит от текущей ширины CRTC).
   - `CursorPosition() (row, col int)` / `SetCursorPosition(row, col int)` — удобные обёртки над теми же регистрами CRTC (индексы 0x0E/0x0F), которые в остальном доступны и напрямую через порты; существуют только чтобы `hookInt10` не работал с сырыми портами вручную.
   - `SetTextRows(rows int) error` (решено в группе 2, tasks.md 2.3) — переключение числа строк текстового режима (25/43/50) перепрограммированием высоты символа (CRTC Maximum Scan Line) поверх уже установленного `SetMode`. Не является отдельным `SetMode`-номером: у настоящего BIOS 80×43/80×50 тоже не имеют собственного video mode number в 00h–13h — они получаются загрузкой знакогенератора меньшей высоты (`INT 10h AX=1112h/1111h`) поверх режима 03h, а не `AH=00h` с новым числом. Заведение выдуманного номера режима для 43/50 строк нарушило бы сценарий «Неизвестный номер режима» спеки `vga` (любой mode number вне задокументированного набора должен считаться ошибкой).
3. **Наблюдательный** — `Frame() Frame` (см. D6) — вычисляет RGB-изображение экрана из текущего состояния регистров/памяти/палитры. Не используется ни гостевым кодом, ни BIOS — только тестами и будущей внешней инфраструктурой (Non-Goals).

**Альтернатива:** реализовать INT 10h как исполнение реального BIOS video ROM поверх портов — отвергнута по той же причине, что и в bios-boot (D1): проект не эмулирует ROM-код, только нативные Go-обработчики.

### D4: Планарная, chained и unchained адресация — общий механизм, не специальные случаи

Классическая VGA-архитектура (4 битовые плоскости) реализуется как есть, чтобы Mode X и подобные комбинации регистров работали автоматически:
- **Sequencer** (0x3C4/0x3C5): Map Mask (индекс 2, биты 0–3) — какие из 4 плоскостей принимают запись; Memory Mode (индекс 4, бит 3 — Chain-4, бит 2 — Odd/Even) — управляет линейной адресацией.
- **Graphics Controller** (0x3CE/0x3CF): Read Map Select (индекс 4) — из какой плоскости идёт чтение; Set/Reset и Enable Set/Reset (индексы 0/1) и Data Rotate/Function Select (индекс 3) — операции над 32-битным «латчем» (4 байта, по одному с каждой плоскости, защёлкиваемые при любом чтении байта видеопамяти); Bit Mask (индекс 8) — какие биты латча реально записываются.
- Запись байта в видеопамять в planar-режиме — не просто `vram[addr] = val`, а: защёлкнуть 4 байта из всех плоскостей по адресу (уже произошло при последнем чтении, либо читается заново — по документированному поведению VGA чтение перед записью не обязательно), применить функцию (Set/Reset или ALU-операция AND/OR/XOR из Function Select с учётом Data Rotate), замаскировать Bit Mask, записать результат в плоскости, разрешённые Map Mask.
- **Chained** (mode 13h): при Chain-4=1 линейный адрес `A` отображается в плоскость `A mod 4`, смещение `A div 4` — обычная 8-бит-на-пиксель адресация без латчей.
- **Unchained/Mode X**: гостевой код сам выключает Chain-4 и включает прямой доступ к 4 планарным банкам по 64 KiB при 256-цветной палитре — этот сценарий не требует отдельного кода в `internal/vga`, если Map Mask/Chain-4/латчи реализованы корректно (см. Risks — это главный источник риска этапа).

### D5: Атрибутный контроллер и DAC — две ступени преобразования цвета

- **Attribute Controller** (0x3C0, порт с флип-флопом индекс/данные, читается через 0x3C1 или обратно 0x3C0 в зависимости от режима): 16 записей палитры (index 0–15) отображают 4-битный атрибут пикселя (или атрибут символа в тексте) в 6-битный DAC-индекс (или в 8-битный индекс напрямую в режиме 256 цветов — Attribute Controller Mode Control, бит 6, «palette bits 5-4 select»).
- **DAC** (0x3C7 read index, 0x3C8 write index, 0x3C9 data ×3 с автоинкрементом после третьего байта): 256 записей по 18 бит (6-6-6 RGB), расширяемых до 8-бит-на-канал при рендеринге кадра (D6) масштабированием `v << 2 | v >> 4`.
- Текстовый режим: атрибутный байт символа (foreground 4 бита, background 3 бита, blink/bright 1 бит) проходит через тот же Attribute Controller индекс foreground/background независимо.

### D6: Framebuffer — вычисляется по запросу (pull), не поддерживается инкрементально

`Frame()` возвращает снимок `{Width, Height int; Pix []byte /* RGBA8888, как image.RGBA.Pix */}`, полностью пересчитываемый из текущего состояния при каждом вызове: для каждого пикселя экрана — определить режим (текст/графика, планарность, разрешение) из регистров CRTC/Sequencer/Graphics Controller, прочитать нужные биты из видеопамяти (текст — из шрифта, D7), пройти Attribute Controller → DAC, записать RGBA. Для визуальной проверки предусматривается вспомогательная функция сохранения `Frame` в PNG (`image/png`, стандартная библиотека).

**Обоснование:** инкрементальное сопровождение готового кадра (перерисовка при каждой записи в память/регистр) существенно сложнее и не даёт наблюдаемой пользователем ценности в этом этапе (нет реального окна с частотой обновления) — решение того же типа, что и D2 роадмапа (интерпретатор вместо JIT: простота и проверяемость важнее производительности, пока нет требования к ней).

### D7: Встроенный растровый шрифт для текстового режима (решено)

VGA-текст рендерится через аппаратный знакогенератор — битовую карту глифов, которую в реальности загружает BIOS ROM при старте. Раз в проекте нет ROM, `internal/vga` включает встроенный шрифт 8×16 (256 глифов, стандартная раскладка кодовой страницы CP437) как Go-данные (`[256][16]byte`, `internal/vga/font8x16.go`, поле `Font8x16`).

Источник — подмножество [GNU Unifont](https://unifoundry.com/unifont/) 17.0.05 (узкие 8×16-глифы, формат `.hex` совпадает байт-в-байт с аппаратным форматом шрифта VGA), сопоставленное с байт-кодами CP437 через официальную таблицу Unicode (`CP437.TXT`) для печатных/расширенных символов и общепринятую таблицу "экранных" символов CP437 для управляющих кодов 0x00–0x1F/0x7F (реальный ROM-шрифт рисует там псевдографику, а не литеральные управляющие символы). Лицензия Unifont — на выбор GNU GPLv2+ с font embedding exception либо SIL OFL 1.1 (обе допускают встраивание производной выборки глифов в код проекта). Полное происхождение, лицензионные тексты и инструмент регенерации (`tools/cp437font`) — `internal/vga/testdata/font/README.md`. Реализовано (не входит в задачу 2.1, сделано на этапе планирования, чтобы не блокировать группу 2).

## Risks / Trade-offs

- [Латчи/write-режимы графического контроллера — самая сложная и наименее очевидная часть VGA; ошибка здесь ломает именно Mode X/unchained-доступ, который целиком зависит от точной семантики] → группа задач 4 tasks.md посвящена только этому, с прицельными юнит-тестами на каждый write mode (0–3) и Set/Reset независимо от режимов, до перехода к Mode X.
- [Нет автоматического эталона (в отличие от CPU SingleStepTests) — по решению пользователя, верификация только юнит-тестами на регистры/форматы плюс ручной просмотр] → каждая задача с визуальным компонентом сопровождается инструкцией по ручной проверке в tasks.md (шаг сохранения кадра в PNG для конкретного тестового паттерна); финальная приёмка этапа включает набор таких дампов для пользователя.
- [«Полный VGA» — по объёму сопоставим с этапом CPU реального режима] → tasks.md разбивает этап на 6 групп с независимой приёмкой каждой, чтобы регресс/токен-бюджет не накапливался на одну финальную интеграцию, аналогично прежним этапам.

# Последний IRQ0: путь гостя и подтверждение причины

> История Go-издания: упоминания Go-команд, путей и цифр ниже относятся к Go-реализации (ai386).

2026-10-14. Независимый read-only разбор записанного исполнения; новых
гостевых запусков и production-правок не было. Артефакты:
`/tmp/ai386-doom-last-irq/last-irq.txt` (header + 511 инструкций),
`/tmp/ai386-doom-last-irq/after.ram`,
`/tmp/ai386-doom-pic-context.log`. Для чтения RAM использован walk PDE/PTE
с CR3=0xb000, аналогичный `readLinear` в `tools/doom/main.go`.

## Установленные наблюдения

Header последнего INTA: EIP=0x46b56f, IF=1, CPL0, CS=0x370, SS=0xc8,
ESP=0x597c; SS hidden-cache base=0x426330, limit=31999, AR=0x4093.
IDTR base=0x81b0, limit=2047. Последний EOI отмечен логом с PC=0x46b566;
по дампу это следующий PC после `OUT DX,AL` на 0x46b565. Сам EOI — 20h,
затем STI на 0x46b56d и CLD на 0x46b56e. IRQ при следующем PC=0x46b56f
согласуется с одноинструкционным STI shadow.

Весь этот путь использует обычный EOI, без AEOI/rotation/poll. Найденные
ранее пробелы поддержки PIC не объясняют данную последовательность сами
по себе.

## Как устроен IRQ wrapper по исполняемому коду

Общий wrapper — 0x46b4e0. EBP получает номер IRQ из EAX. Для IRQ0
таблица callback содержит:

- адрес callback в DWORD linear0x4c71ac: 0x46d210;
- byte flags по linear0x4c71b0: 01h;
- общий счётчик/индекс свободных IRQ-стеков по linear0x4c73e8;
- указатель пула по linear0x4c73f0, меняется блоками 0x1000.

Название «индекс свободных стеков» — вывод из использования переменной,
не восстановленный оригинальный символ. При входе:

```text
46b51c  EBX = [4c73e8]
46b522  ECX = [4c73f0]
46b528  --EBX
46b52f  [4c73e8] = EBX
46b535  [4c73f0] = ECX - 1000h
46b53a  TEST EBX,EBX
46b53c  JLE 46b566       ; обход раннего EOI при EBX <= 0
         если flags.bit0 = 1: обычный EOI
46b566  ... STI; CLD ...
46b59a  LSS ESP,[EDX+8]  ; отдельный callback-стек при индексе >= 0
46b59e  CALL EBX
46b5a0  LSS ESP,[ESP]    ; восстановление стека wrapper
```

При возврате callback EAX копируется в EDX. Указатель пула возвращается,
общая переменная увеличивается. EAX=1 вызывает цепочку старого far-handler;
при другом результате финальный EOI зависит от увеличенного индекса
и flags.bit1:

```text
46b5cf  ++EBX
46b5d2  [4c73e8] = EBX
46b5df  CMP EDX,1
46b5e2  JNE 46b5ed
         иначе PUSHFD; far CALL старого handler
46b5ed  TEST EBX,EBX
46b5ef  JE 46b5fa       ; финальный EOI при EBX == 0
46b5f1  TEST flags,2
46b5f8  JE 46b61e       ; обход EOI при flags.bit1 == 0
46b61d  OUT DX,AL       ; EOI
46b61e  восстановление регистров, RET
```

## Что действительно произошло в последнем IRQ

| Строки trace | Доказанное действие |
|---|---|
| 251–258 | Вошедший IRQ читает индекс 1, уменьшает до 0; JLE обходит ранний EOI. |
| 283–284 | Callback 0x46d210 выполняет INC DWORD[4c7820], затем STI. |
| 328–341 | Callback вернул EAX=0; wrapper увеличил индекс 0→1 и по flags=01h обошёл финальный EOI. |
| 361–418 | Возврат через DPMI-dispatcher восстанавливает сохранённый контекст. |
| 419–420 | IRETD на 0x414ef5 возвращает именно в прерванный 0x46b56f, flags=0x297, ESP=0x597c. |
| 421–441 | Продолжился ранее прерванный внешний wrapper: на собственном стеке вызывает тот же callback. |
| 486–500 | Внешний callback возвращает 0; индекс 1→2; финальный EOI снова обходится. |

Следовательно, один аппаратно подтверждённый внутренний IRQ0 проходит
обе ветки **без EOI**, после чего код корректно возвращается во внешний
wrapper, уже пославший собственный ранний EOI перед прерыванием.
Его финальная ветка также не снимает ISR0. PIC остаётся с ISR0=1;
дальнейшие IRQ0 блокируются.

Финальный snapshot после продолжения содержит:

```text
linear4c73e8 = 4          ; внешние wrapper успели завершить unwind
linear4c73f0 = 00bf6300
linear4c71b0 = 01h
linear4c7820 = 32         ; внутренний счётчик timer callback
linear4c7830 word = 7
linear4c813c = 8          ; игровой счётчик не продвинулся
```

Callback 0x46d210 не просто отсутствует: trace показывает его исполнение.
Он увеличивает собственный счётчик, вызывает зарегистрированные timer
callbacks и возвращает булево «счётчик кратен word[4c7830]» через DIV/SETE.
В рассматриваемых двух возвратах EAX=0, то есть цепочка старого handler
не вызывается. Для окончательного объяснения замороженного игрового
счётчика надо связать его callback с таблицей по 0x4c7670/0x4c76a0;
наличие INC[4c7820] не доказывает INC[4c813c] в каждом IRQ.

## Что ещё не доказано

Установлен точный механизм оставления ISR0, но не причина, по которой
реальный гость достиг индекса 1 перед очередным IRQ. Требуется различить:

1. PIT/cadence допускает столь глубокое вложение из-за неверной частоты
   или продвижения виртуального времени.
2. Гость действительно может достичь этой глубины на согласованном
   режиме 1 МГц; corner-ветка библиотечного wrapper неустойчива на таком
   исполнении. Это нужно воспроизвести и сопоставить с эталоном.
3. Некорректное CPU/stack/context поведение ранее изменило общий индекс
   или удлинило критическую секцию; последний корректный IRETD этого
   не исключает.

Нельзя на основании данной trace объявить CPU/IRET неисправным, заменить
условия в гостевом бинарнике или автоматически снять ISR0 после возврата.
Сохранённый IRETD уже наблюдаемо вернул нужный PC/ESP/flags. Однократный
EOI60h подтверждает блокировку ISR, но не объясняет источник глубины.

## Минимальный кандидат регрессии и следующий probe

Зафиксировать скриптом исходный RAM/PIT/PIC snapshot перед ранним EOI
внешнего wrapper; считать каждое изменение [4c73e8], PIT edge, ACK,
EOI и возврат в прежний PC. Нужен короткий диапазон, включающий переход
индекса 2→1→0, последующее восстановление 0→1→2 и момент зависания.
Такой сигнал различает повреждение индекса и реальное вложение.

Минимальный тест CPU+PIT+PIC может исполнять гостевую последовательность
с IRQ-таблицей, ранним EOI, STI/CLD, смешанными 16/32-битными обработчиками,
LSS callback-stack и возвратом IRET. Исходные значения и PIT-divisor должны
быть взяты из доказанного гостевого пути. Тест должен требовать сохранность
каждого frame/регистра, соответствие количества EOI/ACK и продвижение
счётчика. Само наличие library-ветки без EOI нельзя исправить внутри PIC:
сохранять ISR после ACK до требуемого EOI — его нормальная семантика.

Если depth достигается только при слишком частых PIT edges, регрессия
должна находиться на seam PIT→virtual-time→CPU delivery, с той же реальной
последовательностью программирования PIT. Если индекс меняется при
корректных edges/frame counts — минимизировать виновную CPU-команду.

## Завершение подтверждения 2026-10-14

Предыдущие разделы фиксируют этап до однофакторного probe. Причина
подтверждена исключением повторных внутренних PDE/PTE обходов из
приближённого времени устройств: на 1 МГц timer 142→326, INTA 3622→4358.
Трансляция, права и A/D не менялись. Регрессия одинакового paged/flat
guest work была красной при старом clock и зелёной после разделения
`ClockCycles`/`Cycles`. Детали: [результат probe](research.md#результат-однофакторного-эксперимента-времени),
[принятый дизайн](../../openspec/changes/bios/design.md).

Финальные timer/input матрицы 2×2 и живые Linux/FreeBSD прошли.
PIC не менялся: ISR продолжает требовать гостевой EOI, принудительного
снятия ISR или патча wrapper нет. Это исправление приближённого clock,
а не заявление о точности DX4/TLB. [Матрица](timer-results.md).

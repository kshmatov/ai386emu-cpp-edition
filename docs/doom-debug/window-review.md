# Review: оконная приёмка Doom

> История Go-издания: упоминания Go-команд, путей и цифр ниже относятся к Go-реализации (ai386).

Проверено 2026-10-14. Объём: `tools/doom/main.go` (`-window`/`-warp`,
`runDoomWindow`), `window.py`, `window_flags_test.go`, `window.md`.
Production frontend не изменён; его завершение worker проверено чтением
`internal/frontend/window_desktop.go`. Review не закрывает живую приёмку.

## Standards

Блокирующих нарушений документированных правил не найдено. Инструмент
использует текущие config/frontend/machine API, сохраняет отдельную копию HD
и артефакты в новом каталоге. Headless-сборка отказывает в `-window` до чтения
конфигурации и создания HD; отказ покрыт тестом. Режимы и бюджеты являются
явными диагностическими параметрами, display scale/FPS берутся из TOML.

Python использует X11/XTest helpers из поддерживаемого frontend-smoke
скрипта через ограниченную AST-выборку: выполняются определения до первой
проверки sys.argv, synthetic guest main routine не исполняется. Это зависимость
от структуры helper-файла, но текущая граница однозначна, и ошибка поиска
границы прекращает сценарий. Нового runtime dependency не добавлено.

## Spec и отсутствие конкурентного доступа

Перед окном harness выбирает FreeDOS и запускает оригинальный Doom
через PS/2 на копии HD. Готовность проверяет продвижение таймера, разрешённую
relocation, сигнатуру I_GetTime в текущем линейном отображении, player/mobj
back-reference, стартовые координаты E1M1, opcode Escape branch и непустой
320×200 кадр. Неинициализированный либо чёрный кадр не считается готовностью.

До `frontend.Run` CPU/RAM принадлежат вызывающему потоку. Во время окна
единственным владельцем VM становится frontend worker: harness не читает
RAM, CPU, VGA или map счётчиков и не вызывает `Machine.KeyEvent` параллельно.
`frontend.Run` после RunGame вызывает `session.stop`, ожидающий `<-done`.
Поэтому последующие чтения и ограниченное ожидание клиентского DPMI mapping
выполняются после join. IRQ map меняется callback этого же worker и читается
только после завершения. Добавленного concurrent VM access не найдено.

`linearBytes`/`readLinear` читают raw RAM и обходят таблицы без обращения
через CPU: диагностические чтения не меняют A/D, CR2 и гостевые регистры.
Harness не патчит код, globals, player или меню. После закрытия проверяются
сохранность object pointer, изменение координат, расход патронов, конечное
menuactive=0 и IRQ1 INTA; сохранены RAM/PNG/регистры до и после окна.

## X11 ownership и границы PASS

Драйвер требует специально выделенный задаче `DISPLAY=:172` и проверяет
`_NET_WM_PID` найденного ai386-окна против PID только что запущенного процесса
до raise/focus/input. При другом PID сценарий прекращается. XTest события
посылаются внутри этого выделенного display; запуск на общем пользовательском
desktop не входит в документированную процедуру. Проверка имени DISPLAY
сама по себе не создаёт и не доказывает владение сервером: выделенный Xvfb
должен быть создан задачей перед запуском, как требует `window.md`.

Закрытие адресовано проверенному window ID через WM_DELETE_WINDOW.
Драйвер требует окончательный exit0 и маркер `DOOM-WINDOW PASS` в логе,
а не только найденное окно или возвращённую PTY-сессию. При ошибке собственный
процесс завершается; финальный release keys ограничен живым найденным своим
окном. Чужие окна не выбираются для focus или адресного close.

Конечный menuactive=0 не доказывает промежуточный показ меню. Общее число IRQ1
тоже не идентифицирует отдельное действие Escape. Первоначальный JEMMEX-прогон
`/tmp/ai386-doom-window-jemm1m-final` имел Go PASS, движение и стрельбу, но
`menu.png` не содержал меню. Этот результат является partial, оконная приёмка
Escape им не подтверждена.

Повторный review усиленного `window.py`: после первого Escape драйвер ждёт
реального меню на X11-снимке, затем посылает второй Escape и ждёт исчезновения
меню; только после обеих фаз отправляются Up и Control_L. Каждая фаза имеет
60-секундный deadline и проверяет живость процесса; отсутствие overlay
прекращает сценарий без `result.txt` PASS.

`menu_fraction` поддерживает именно PNG данного helper: RGB8, filter0,
несколько IDAT, проверка размера распакованных строк. Оно считает красные
пиксели r≥96, r>2g, r>2b только в x28–76%/y30–80% снимка. Status bar начинается
ниже этого кропа; масштаб задаётся относительными координатами. Порог >10%
предназначен для зафиксированного Doom меню в E1M1 и не является общим OCR.
Визуальная проверка PNG остаётся частью приёмки.

Независимо применён финальный detector к сохранённым реальным снимкам:

| Снимок | Доля красного в кропе | Меню по порогу |
| --- | --- | --- |
| Safe `menu.png` | 0.264300 | да |
| Safe `game.png` / `menu-closed.png` | 0.003779 | нет |
| Старый JEMM `menu.png` | 0.003779 | нет |
| Старый JEMM `fire.png` | 0.047752 | нет |

Safe и JEMM ссылки выше относятся к каталогам
`/tmp/ai386-doom-window-safe1m-final` и `/tmp/ai386-doom-window-jemm1m-final`.
Визуально проверены Safe menu, старый JEMM menu и его fire: detector принимает
красный шрифт меню и отвергает обычный E1M1 и вспышку пистолета/кровь в этих
reference кадрах. Между положительным образцом и порогом есть достаточный
запас; отрицательный fire остаётся ниже порога.

Финальные живые прогоны усиленного драйвера завершены с exit0:
`/tmp/ai386-doom-window-jemm1m-menu-final` (mode2) и
`/tmp/ai386-doom-window-safe1m-menu-final` (mode4), оба при 1 МГц.
Независимо визуально просмотрены обе пары `menu.png`/`menu-closed.png`:
меню Doom поверх E1M1 появляется, затем исчезает. Driver зафиксировал
0.2643→0.0038 в каждом запуске. Post-join результат: изменение координат,
патроны 50→47 и IRQ1 68→310 в JEMM; патроны 50→42 и IRQ1 68→314 в Safe;
конечное меню 0. `result.txt` и процессные логи подтверждают штатный
WM_DELETE_WINDOW, Go PASS и exit0. Старый JEMM partial этим не переименован.
GUI 100 МГц этим review не считается проверенным.

Живой оконный прогон и визуальная проверка снимков выполняются отдельно
от этого review. Xvfb подтверждает настоящий frontend/host event path,
но не физический монитор, звук или все загрузочные/частотные комбинации.

## Проверки

```sh
GOCACHE=/tmp/ai386-status-go-cache go test -race ./tools/doom
GOCACHE=/tmp/ai386-status-go-cache go vet ./tools/doom
```

Пакет прошёл с race (2.029s), vet без ошибок. Финальный `window.py` успешно
разобран через Python AST; detector проверен на четырёх типах настоящих PNG.
`git diff --check` прошёл. Эти проверки не заменяют
живой desktop run; desktop build и его runtime проверяются приёмкой.
Открытых блокирующих standards/spec замечаний к проверенному коду нет.

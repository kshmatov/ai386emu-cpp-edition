## Исходные сведения до исправления

- [Приёмка 2026-10-11](../doom-acceptance-2026-10-11.md): JEMMEX останавливается в ожидании
  игрового времени; Safe Mode показывает E1M1 и движущуюся демозапись.
- Там же: IRQ1 маскирован, Esc не открывает меню; записанный PCM содержит
  только тишину. Причины ещё не установлены.
- Изолированная диагностическая консоль находится в
  `build/freedos/debug-install/main.go`; принимает JSON-команды, клавиши,
  текст, бюджет инструкций, сохраняет RAM и PNG. Это локальный игнорируемый
  инструмент предыдущей проверки, его требуется заменить воспроизводимым
  инструментом в репозитории.
- Исходный HD: `build/freedos/freedos-ready.img`; конфигурация:
  `build/freedos/freedos-ready.toml`, RAM 16 МиБ.

## Исходные вопросы исследования

1. Какой гостевой адрес содержит игровой счётчик в текущем запуске?
2. На какой границе исчезает продвижение времени в JEMMEX?
3. Какая последовательность гостя оставляет IRQ1 маскированным?
4. Доходит ли известный эффект до буфера DMA?

Предположения о причине не приняты до воспроизведения и минимизации.

## Воспроизведение 2026-10-14

Изолированная копия HD в `/tmp/ai386-doom-loop/`, режим 2, 1 МГц.
FreeDOS достигла `C:\>`; выполнена `DOOM -NOSOUND`. Между `doom2.ram`
и `doom3.ram` исполнены ещё 2 000 000 гостевых шагов.

- CR3 = `0xb000`, EFLAGS = `0x246`, CPU исполняет цикл `0x47798a–0x477a18`.
- Загруженная функция `0x471c10`: `mov eax,[0x4c813c]; ret`.
- Чтение `0x4c813c` через таблицы страниц: `8 → 8`.
- BIOS ticks: `16178 → 16178`; IVT8: `1c11010f`.
- Python assert `after > before` выполнен и завершился
  `AssertionError: Doom timer stopped despite guest execution`.

Ранжированные гипотезы (ни одна пока не подтверждена):

1. PIC блокирует IRQ0 из-за состояния обслуживания/EOI: запросы остаются
   в IRR при установленном ISR0. Проверка — снимки PIC и реальные INTA.
2. PIT прекращает периодические импульсы: IRQ0 не появляется в IRR при
   свободном ISR. Проверка — latch/status и счётчики при продвижении.
3. CPU теряет доставку после VM86/DPMI: PIC имеет доступный запрос при IF,
   но реального INTA нет. Проверка — обёртка существующего callback INTA.
4. Обработчик исполняется, но обновляет другое состояние: INTA и обращения
   к обработчику продолжаются при неизменном игровом таймере. Проверка —
   ограниченная трасса обработчика и адреса данных.

## Результат однофакторного эксперимента времени

Полная трасса: [IRQ0 research](irq0-research.md). PIC работает согласно
EOI гостя, а вложенный wrapper обходит EOI при исчерпании индекса стеков.
JEMMEX с исходной моделью100МГц: таймер `8→16`, INTA `302→336`.
1МГц после исправления IRQ1: по-прежнему `8→8`.
При исключении только внутренних readBus32/writeBus32 обхода PDE/PTE
из условных тактов на1МГц: `142→326`, INTA `3622→4358`,
артефакты `/tmp/ai386-doom-walk-time-probe/`.

Это подтверждает влияние учёта повторных программных обходов страниц
на чрезмерную вложенность IRQ. [Исходный контракт времени](../../openspec/changes/archive/2026-09-16-pit-clock/design.md)
приближённый; его уточнение и отдельная метрика ClockCycles записаны
в scoped design до постоянного исправления. Функциональное состояние CPU
не изменяется; аппаратная модель TLB не добавляется.

## Внешний источник для сопоставления игрового цикла

[Исходный `d_net.c` id Software](https://github.com/id-Software/DOOM/blob/master/linuxdoom-1.10/d_net.c)
описывает `NetUpdate`: считывание `I_GetTime`, вычисление разницы с
`gametime`, создание новых игровых тактов при положительной разнице.
Это Linux Doom 1.10: источник объясняет связь времени с игровым циклом,
но адреса и реализацию DOS Doom 1.9 необходимо доказать по гостевому коду.

## Подтверждённые ответы и текущая приёмка

1. I_GetTime загруженного DOS Doom подтверждает timer по 4c813ch в JEMMEX
   и 1e013ch в Safe Mode; подпись и текущая mapping проверяются заново.
2. Искусственное ускорение PIT повторными программными page walks
   вызывает чрезмерную вложенность JEMMEX IRQ wrapper и пропущенный EOI.
   Минимальный clock fix и paged/flat регрессия прошли.
3. Исходный BIOS не устанавливал IRQ1 handler и оставлял mask FE. Теперь
   handler установлен до открытия IRQ1; гостевые mask/chaining сохранены.
4. Данные эффекта доходили до DMA, но reset master/voice 4/31 дважды
   округлял сигнал в тишину. Документированные CT1745 reset levels
   восстановлены; настоящие выстрелы проходят полную PCM матрицу.

Результаты и границы: [актуальный отчёт Doom](../doom-acceptance.md).
Исходные гипотезы выше сохранены как история диагностики и не обозначают
нынешнее состояние исправленной сборки.

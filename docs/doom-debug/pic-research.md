# PIC: исследование после воспроизведения остановки времени Doom

> История Go-издания: упоминания Go-команд, путей и цифр ниже относятся к Go-реализации (ai386).

Дата: 2026-10-14. Использован цикл diagnosing-bugs: исходный симптом уже
воспроизведён отдельной Doom-сессией; ниже проверяются конкретные аппаратные
семантики. Производственный код при этом исследовании не изменялся.

## Исходное наблюдение и границы вывода

По сообщению root/doom_repro: `/tmp/ai386-doom-loop/doom2.ram` и `doom3.ram`,
CR3=0xb000, игровой счётчик по linear 0x4c813c остаётся равен 8 после
2 млн инструкций; IF=1, цикл по 0x477a01. Это свидетельство остановки
игрового времени, но не доказательство причины на границе PIT/PIC/CPU.
Ранжированные root-гипотезы: PIC блокирует IRQ0; PIT перестал давать edges;
CPU теряет IRQ при VM86/DPMI; обработчик меняет другую память.

## Проверенные требования Intel

Первичный источник: [Intel 8259A datasheet](https://www.pcjs.org/documents/datasheets/intel/INTEL_8259A_PIC.pdf),
печатные страницы 11 и 14–17, Figure 7 и таблица OCW2/OCW3.

- ICW4.AEOI=1 снимает ISR при завершении acknowledge, без программного EOI.
- OCW2 A0h выполняет non-specific EOI и переносит обслуженный IRQ в конец
  приоритета; E0h–E7h делает specific EOI с ротацией.
- C0h–C7h назначает указанную линию последней; следующая становится первой.
- 80h включает ротацию AEOI; 00h выключает её.
- OCW3.P=1 переводит следующее чтение в poll acknowledge. Результат: D7
  показывает наличие запроса, D0–D2 — линию; соответствующие IRR/ISR меняются.
- Обычный non-specific EOI снимает самый приоритетный активный ISR; сравнение
  приоритетов после ротации должно учитывать текущий порядок.

Эти требования определяют probes ниже. Специальные маски, buffered mode,
level-triggered mode и SFNM не проверялись в этой работе.

## Что делает текущий код

Проверялась копия pic.go (`../internal/pic/pic.go`) с SHA-256
`55cf81cc04c644979232c0c27b4388ef192db2c31b8bf396b2acb2c6f248b6c0`.

- `dataWord` завершает ICW4 без сохранения AEOI. Комментарий о неиспользовании
  прочих битов гостевой ОС является предположением, а не доказательством.
- `Acknowledge` всегда устанавливает ISR обслуженной линии.
- `command` принимает EOI только при верхних битах 20h/60h; A0h/E0h не
  выполняют даже снятие ISR.
- `candidate`, `masterLine`, `clearHighestISR` используют фиксированный
  порядок 0→7; OCW2 set-priority игнорируется.
- `command` распознаёт только OCW3 register-read 0Ah/0Bh; poll не сохраняется,
  а `In` читает IRR/ISR без acknowledge.

## JEMMEX: доступное свидетельство и его ограничения

Локальный `/tmp/ai386-fdi-files/FREEDOS/BIN/JEMMEX.EXE` содержит строку
`JemmEx v5.85 [01/09/25]`, SHA-256
`4b3046802518739652e0d90b92bbe240ac58870c572e3db9f6bbb94cc7d10ec2`.
Это извлечённый файл; соответствие байтам в текущем рабочем HD отдельно
не подтверждалось.

В доступном upstream
[INIT.ASM](https://raw.githubusercontent.com/Baron-von-Riedesel/Jemm/master/src/INIT.ASM)
IOBM содержит нули для PIC 20h/21h и A0h/A1h: исходная bitmap не захватывает
эти порты. Это не исключает позднюю установку внешнего trap handler.
В [JEMM32.ASM](https://raw.githubusercontent.com/Baron-von-Riedesel/Jemm/master/src/JEMM32.ASM)
reboot-путь использует Out20=0Bh, читает ISR1 и посылает обычный EOI20h.
Оба источника относятся к upstream master, не к доказанно идентичной v5.85
сборке. Получить v5.85 через raw URL в этой сессии не удалось.

Не найдено доказательства, что воспроизводимый Doom/JEMMEX-путь включает
AEOI, rotate+EOI или poll. Поэтому перечисленные расхождения пока являются
дефектами поддержки PIC без установленной причинной связи с остановкой игры.

## Следующие probes на реальном гостевом пути

1. Сохранить ограниченный I/O trace PIC20/21/A0/A1 от старта игры до
   остановки: шаг, CS:EIP, CPL/VM, направление, значение. ICW4 распознавать
   только по стадии ICW-последовательности; число 03h вне этой стадии — IMR.
   Отдельно посчитать guest Out20=A0h/E0h–E7h и OCW3 с P=1.
2. На границе остановки снять IRR/ISR/IMR master и slave вместе с числом
   PIT edges, PIC ACK и CPU entry в IRQ0. Чтение через OCW3 изменяет выбор
   регистра, поэтому восстановить его либо использовать временный snapshot.
3. Если edges растут, IRR0=1, IMR0=0, ISR0=1, ACK не растёт — блокировка
   доказана на PIC. Если ISR0=0 и обычный фиксированный приоритет, ISR1/ISR2
   не должны блокировать IR0: такая гипотеза опровергнута текущим кодом.
4. Для AEOI-гипотезы требуется **наблюдённый** ICW4 bit1=1; изменение только
   семантики AEOI должно возобновить ACK и игровой счётчик. Если bit1=0,
   AEOI не объясняет этот запуск.
5. Для rotate-EOI-гипотезы требуется фактический A0h/E0h–E7h на командном
   порту после принятия IRQ; compare до/после должен показать снятие ISR.
   Отсутствие таких команд исключает этот механизм из причины запуска.
6. Для poll-гипотезы нужны OCW3.P и последующее чтение, затем использование
   результата guest-кодом. Без poll-команд это независимый дефект поддержки.
7. Если PIC ACK растёт, а CPU entry нет — исследовать CPU delivery/shadow/
   VM86 transitions. Если entry растёт, сравнить CR3 и физический адрес
   записи обработчика с отображением linear0x4c813c. Если PIT edges не
   растут — PIC-гипотеза не объясняет первичную остановку источника.

Однократный принудительный EOI60h для IRQ0 может различить блокировку ISR,
но является диагностическим вмешательством: сам по себе успех не доказывает
ни ошибку PIC, ни корректность гостевого EOI. Требуется trace исходной
последовательности и повтор исходного запуска без вмешательства после фикса.
